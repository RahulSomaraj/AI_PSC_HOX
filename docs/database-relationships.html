How the PSC Tables Relate

Nineteen tables in three loosely-joined groups. This document traces every foreign key, what each one does on delete, and the four places where the schema does not constrain what the code assumes.

01 The three groups

The schema is not one connected graph. It is three clusters that meet only at users and course. Knowing which cluster a table belongs to explains most of its delete behaviour and most of its naming.

Group A hangs entirely off users. Group B is the older course-and-quiz track, hanging off course and users. Group C is the newer PSC exam catalog, joined to a shared academic hierarchy by the syllabus. B and C never touch — which is the single most consequential fact about this schema.

Soft delete is not what TypeORM thinks it is

users.deletedAt is a plain @Column, not a @DeleteDateColumn. TypeORM therefore does not filter it automatically — every query has to pass deletedAt: IsNull() by hand, and any query that forgets will return deleted users.

This already leaks: GET /aspirant-profiles joins relations: ['user'], and a soft-deleted user still arrives attached to their profile. Every other soft-deleted table in this schema uses a real @DeleteDateColumn and filters itself.

Two different things are both called an exam

exams in this group is an attempt session — one user's run through a set of questions. The catalog entity in Group C is exam_posts, named that way precisely because exams was already taken and holds live data.

The foreign keys pointing at exam_posts are still named exam_id, matching the domain language. So exam_stages.exam_id means an exam post, while exams.id means an attempt. They are unrelated.

Why the academic tables are not owned by an exam

“Indian Constitution” is one row in subjects. The Degree Level, Plus Two Level, SI and LDC syllabi all reach it through exam_syllabus_items. There is no per-exam copy such as “SI Constitution”. That is what makes the item table a bridge rather than a child.

Three unique indexes on one table

An item can be mapped at three depths, so topic_id and subtopic_id are nullable. Postgres treats NULLs in a unique index as distinct values, so a single index over those columns would happily accept duplicates. The table therefore carries three partial unique indexes, one per depth — subject only, subject + topic, and subject + topic + subtopic.

06 Where the schema does not match the intent

Four gaps that the foreign keys cannot express, ordered by what they cost.

  1. Group B and Group C are not connected. An attempt (exams) points at a course, never at an exam_stage. A student can sit “a random 30 from course X”, but not “the SI Preliminary paper”. The catalog describes exams nobody can yet take, and the attempt engine runs exams the catalog does not know about. Closing this is the single largest piece of work the schema implies.
  2. Negative marking is modelled but never applied. exam_stages.negative_mark exists and holds real values, which is how PSC papers actually score. The grading code in the attempt engine never reads it, because it cannot reach a stage from an attempt.
  3. Question selection has no referential integrity. exams.questionIds is a JSON array of integers, not a join table. A question can be deleted while an attempt still references it; nothing at the database level objects.
  4. Audit columns are unconstrained. Every table in Group C carries created_by, updated_by and deleted_by as plain int. They hold user ids taken from the JWT but have no foreign key, so they can point at users who never existed.
